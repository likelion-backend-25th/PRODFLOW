# 견적 PDF 설계

## 1. 범위와 진행 상태

견적 PDF 양식, DRAFT 초안 저장과 DB ID 기반 견적번호, OpenPDF와 한글 폰트 준비 기준을 정리한다.
DRAFT 최초 저장·수정, OpenPDF 생성, S3 저장·재생성·미리보기 URL API를 구현했다. 프론트 모달 연결과 최종 발송은 아직 구현하지 않았다.
3절의 전체 흐름은 목표 설계이며 이번 구현 범위는 5절에 구분한다. 별도 번호 발급 테이블은 도입하지 않는다.

참고 문서는 [기획서](../01_planning/01_proposal.md), [업무 흐름](../01_planning/04_business_process.md),
[ERD](02_erd.md)이다. 견적은 생산 자리를 차지하지 않으며 수주 등록부터 수량을 반영한다.

## 2. 한 페이지 양식

### 2.1 배치

A4 세로(210 × 297mm), 사방 여백 15mm를 기준으로 한다.
흰 배경, 검은 본문, 연한 회색 표 머리글을 사용하며 금액과 문서 제목을 강조한다.
본문은 나눔고딕 Regular, 제목과 합계는 Bold로 표시한다. 아래 크기는 실제 출력 검증 전의 설계 기준이다.

```text
┌────────────────────────────────────────────────┐
│ 회사명 / 로고                         견 적 서 │
│ 견적번호          발행일              유효기간 │
├───────────────────────┬────────────────────────┤
│ 수신 거래처           │ 공급자                 │
│ 회사명 / 담당자       │ 회사명 / 담당자        │
│ 연락처 / 이메일      │ 사업자번호 / 연락처    │
│                       │ 주소                   │
├───────────────────────┴────────────────────────┤
│ 견적 총액                         0원 (VAT 포함)│
├────┬──────────┬──────┬─────┬────────┬──────────┤
│번호│ 품목명   │ 기종 │수량 │ 단가   │ 금액     │
├────┴──────────┴──────┴─────┴────────┴──────────┤
│ 품목 행                                      │
├────────────────────────────────────────────────┤
│                      공급가액 / 부가세 / 총액 │
├────────────────────────────────────────────────┤
│ 희망 납기 / 예상 납기                          │
│ 납기 안내 문구                                │
└────────────────────────────────────────────────┘
```

| 영역 | 출력 내용 | 표시 기준 |
|---|---|---|
| 제목 | 견적서, 공급자 회사명, 선택적 로고 | 제목 22pt, 로고가 없으면 회사명만 표시 |
| 문서 정보 | 견적번호, 발행일, 유효기간 | 날짜는 `yyyy-MM-dd`, 한국 날짜 기준 |
| 수신 거래처 | 회사명, 담당자, 연락처, 이메일 | 실제 발송 이메일은 모달에서도 별도 강조 |
| 공급자 | PRODFLOW, 작성 직원, 사업자번호, 주소, 연락처 | 직원명은 created_by, 사업자번호·주소·연락처는 예시 표시 |
| 총액 강조 | 부가세 포함 총액 | 천 단위 구분, 원 단위 |
| 품목 표 | 번호, 품목명, 기종, 수량, 단가, 금액 | 숫자는 우측 정렬, 단가의 VAT 기준 명시 |
| 금액 요약 | 공급가액 합계, 부가세, 총액 | 서버의 기존 금액 계산 결과 사용 |
| 일정 | 희망 납기, 예상 납기 | 내부 생산 시작·완료 예정일은 기본 양식에서 제외 |
| 안내 | 예상 납기는 견적 시점 기준이며, 수주 등록 시 재확인됩니다. | 생산 자리 예약으로 오해하지 않도록 표시 |

### 2.2 현재 데이터와의 연결

저장된 초안의 데이터로 PDF를 구성한다. 정식 발송 시에는 사용자가 확인한 버전의 데이터와 PDF를 사용한다.

| PDF 항목 | 현재 코드의 값 또는 준비할 값 |
|---|---|
| 견적번호 | `Quotation.quotationNo`; 최초 초안 저장 후 DB ID로 확정 |
| 발행일 | 이번 구현은 `createdAt.toLocalDate()` 사용. 기존 감사 시각의 날짜이며 별도 발행일 컬럼은 추가하지 않음 |
| 유효기간 | `Quotation.validUntil` |
| 거래처명 | `Quotation.client.company` |
| 거래처 담당자 | `Quotation.clientName` |
| 이메일·연락처 | `Quotation.clientEmail`, `Quotation.clientPhone` |
| 거래처 주소 | `Quotation.clientAddress` |
| 품목명·기종 | `QuotationItem.productName`, `QuotationItem.deviceName` |
| 수량·단가·금액 | `QuotationItem.quantity`, `unitPrice`, `lineAmount` |
| 공급가액·부가세·총액 | `QuotationDto.DetailResponse`의 `supplyAmount`, `vatAmount`, `totalAmount` |
| 희망·예상 납기 | `requestedDueDate`, `estimatedDueDate` |
| 공급자 정보·로고 | 회사명 PRODFLOW, 담당자 `createdBy`, 나머지 예시 데이터. 로고 미적용 |

현재 견적 품목에는 독립된 규격 스냅샷이 없다. `deviceName`은 기종이므로 규격으로 바꾸어 표시하지 않는다.
품목 표는 현재 저장 데이터에 맞춰 품목명·기종으로 구성한다.
거래처 회사명은 현재 연결된 거래처에서 조회하므로, 향후 미리보기·발송에서는 확인 당시 값을 별도로 보관해야 한다.

### 2.3 금액 표시

- `vatIncluded`는 입력 단가의 VAT 포함 여부다. 최종 `lineAmount`와 `totalAmount`는 두 경우 모두 VAT 포함 금액이다.
- 따라서 품목 표의 마지막 열은 공급가액으로 단정하지 않고 **금액(VAT 포함)**으로 표시한다.
- 단가 열은 `vatIncluded=true`이면 **단가(VAT 포함)**, 아니면 **단가(VAT 별도)**로 표시한다.
- 총액 아래에 공급가액·부가세를 분리해 표시하되 PDF에서 별도 반올림 공식을 만들지 않는다.
- 기존 계산은 품목별 VAT 적용·원 단위 반올림 후 합산한다. PDF 때문에 이 규칙을 변경하지 않는다.

### 2.4 한 페이지 제약과 미확정 정보

- 품목 표에는 본문 10pt를 기준으로 사용하고 품목명·기종은 줄바꿈을 허용한다.
- 최대 품목 수는 아직 정하지 않았다. 긴 품목명과 기종을 넣은 실제 출력으로 정해야 한다.
- 한 페이지가 넘치는 입력을 자동 축소하거나 잘라서 발송하지 않는다. 이후 구현에서 초과 입력의 안내·검증 기준이 필요하다.
- 공급자는 요청에 따라 PRODFLOW와 예시 사업자번호·주소·연락처를 표시한다. 각 예시 값에는 `(예시)`를 붙이며 로고·도장은 넣지 않는다.
- 계약금·잔금·입금 계좌는 이번 견적 기본 양식에서 제외한다. 별도 요구가 있을 때 추가한다.

## 3. 초안 저장과 견적번호

### 3.1 현재 코드와 설계 변경

`QuotationService.create()`는 견적과 품목을 DRAFT로 저장하고 DB ID로 `QT-yyyyMMdd-id` 번호를 확정하도록 변경했다.
최초 `발송 전 확인`용 PDF API는 이 저장 트랜잭션이 커밋된 다음 PDF를 생성한다.
별도 일별 순번·번호 선발급 테이블과 별도의 견적 입력 미리보기 테이블은 도입하지 않는다.
기존 견적번호와 발급 형식은 유지한다. 초안 삭제로 ID가 비어도 재사용하지 않는다.
DRAFT 상태와 최초 저장·같은 초안 수정은 코드에 반영했다. 최종 발송 전환은 후속 작업이다.

### 3.2 화면과 저장 흐름

1. `발송 전 확인`: 권한·입력값·품목·납기를 검증하고 견적·품목·총액을 DRAFT로 저장한다. 신규 거래처도 이때 등록한다.
2. 최초 저장한 ID로 번호를 확정한다. 번호의 날짜는 최초 초안 생성일이다.
3. 저장된 데이터로 PDF를 생성해 `quotations/{quotation_no}.pdf`에 업로드한다. 최초 생성·재생성 실패 시 초안은 유지하지만 발송은 허용하지 않는다.
4. 모달에서 거래처명·강조된 실제 수신 이메일·PDF를 확인한다.
5. `돌아가서 수정`: 같은 초안의 ID와 번호를 유지한다. 기존 PDF는 발송 불가로 만들고 재확인 시 내용을 갱신해 새 PDF를 생성한다.
6. 초안의 품목·수량·단가·VAT가 바뀌면 총액을 재계산한다. 발송 확정 이후에는 기존 원본 금액 유지 규칙을 적용한다.
7. 최종 `견적 발송`: DRAFT 상태·권한·확인한 문서 버전·유효기간·최신 납기를 재검증한다.
8. 통과하면 같은 견적을 SENT로 확정하고 동일한 S3 파일을 발송본으로 유지한다. 별도 정식 경로로 복사하지 않는다. DB 커밋 후 해당 PDF를 첨부해 이메일을 보내고 시도 결과를 client_noti_log에 기록한다.
9. 최종 검증 실패 시 DRAFT를 유지한다. 내용이 달라지면 새 PDF 확인을 거치며 임의로 바꾼 문서를 발송하지 않는다.
10. 이메일 실패 시 SENT와 정식 PDF를 유지한다. 중복 요청 방지와 명시적 재발송을 구분한다.

### 3.3 상태와 접근 규칙

- DRAFT는 수정·PDF 준비·초안 삭제만 허용하며 승인·거절·수주 등록·SENT용 납기 재산정은 허용하지 않는다.
- SENT 이후에는 일반 초안 수정 API를 사용할 수 없다. 기존 상태별 처리 규칙을 적용한다.
- 초안 목록과 발송 확정 견적은 구분해야 한다. 초안 접근·수정 권한의 세부 범위는 API 설계에서 확정한다.
- 초안을 삭제할 때 관련 품목과 PDF도 정리하지만 신규 등록된 거래처는 함께 삭제하지 않는다.
- 초안 보관·정리 기간은 미확정이다. SENT만 EXPIRED로 바꾸는 만료 배치와 분리한다.
- 모든 견적은 생산 자리를 차지하지 않는다. 등록된 수주부터 다음 계산에 반영한다.

### 3.4 PDF·날짜·장애 처리

- 발행일은 PDF 준비 시 한국 날짜로 둔다. 유효기간은 그 날짜+7일 또는 +14일로 계산한다.
- 날짜가 바뀌면 같은 초안에서 발행일·유효기간·납기를 갱신한 PDF를 다시 확인한다. ID와 번호는 유지한다.
- S3 키는 `quotations/{quotation_no}.pdf`로 계산한다. 견적번호당 파일 하나를 관리하며 업로드 성공 후 `quotation.pdf_object_key`에 객체 키를 저장한다. 만료되는 Presigned URL과 과거 PDF 버전은 보관하지 않는다.
- 수정 후 새 PDF를 메모리에서 생성하는 데 성공하면 기존 S3 파일 삭제를 시도한 뒤 같은 키에 업로드한다. 삭제가 실패해도 업로드를 진행하며 남아 있는 파일은 덮어쓴다.
- PDF 생성·업로드 실패 시 저장한 초안을 유지한다. 재생성 API로 한 번 재시도하고 다시 실패하면 오류 메시지와 재시도 버튼을 표시한다. 삭제 실패만으로 재생성을 요구하지 않는다.
- 생성·수정·재시도 시작 시 이전 미리보기와 URL을 비운다. 이번 업로드가 성공한 경우에만 새 미리보기를 표시하며 S3 파일 존재 여부만으로 업로드 성공을 판단하지 않는다.
- S3는 비공개로 두고 기간 제한 조회 URL로 표시한다. 프론트는 이전 미리보기를 해제하고 조회 응답의 캐시 정책을 적용해 최신 PDF를 표시한다.
- 초안 수정·재생성 시작 시 `pdf_object_key`를 NULL로 바꾸고 별도 커밋한다. 현재 초안의 업로드와 URL 발급이 성공한 후에만 경로를 저장한다. 경로가 NULL이면 파일이 남아 있어도 조회하지 않는다. 별도 `pdf_ready` 컬럼은 두지 않는다.
- 같은 견적의 PDF 업로드·초안 수정·발송 확정은 동시에 실행되지 않도록 직렬화해야 한다. 여러 서버에서도 적용되는 DB 잠금 또는 작업 점유 방식을 구현 전에 정한다.
- 업로드 성공 후 DB 기록이 실패하면 발송 불가 상태를 유지하고 재생성한다. 업로드 응답 유실·서버 중단으로 완료 여부가 불확실해도 준비 완료로 추정하지 않는다.
- 모달은 확인 당시 초안 버전을 최종 요청에 보내고 서버는 현재 초안·PDF 준비 기준과 비교한다. 이는 DB의 동시 수정 검증이며 S3의 과거 파일 보관과는 별개다.
- SENT 확정 이후에는 같은 파일을 초안 수정 경로에서 덮어쓰거나 정리하지 않는다. 현재 발송 요청의 첨부 파일을 읽는 동안에도 덮어쓰기를 차단한다.
- DRAFT 파일과 SENT 파일이 같은 접두사를 사용하므로 `quotations/` 전체에 일괄 자동 삭제 규칙을 적용하지 않는다. 초안 상태를 확인하는 별도 정리 작업을 사용한다. 보관 기간은 미정이다.
- 견적 확정과 함께 발송할 작업을 DB에 기록하는 방식을 권장한다. 작업 테이블·재시도·중복 처리의 상세 구조는 미확정이다.
- client_noti_log는 현재 ERD대로 SENT·FAILED의 발송 시도 결과를 기록한다. 견적의 SENT 상태와 실제 메일 전달 성공을 구분한다.
- 메일 전송 결과가 불확실한 경우까지 무조건 자동 재발송하지 않는다. 제공자의 중복 방지 기능과 확인 방식을 발송 구현 단계에서 검토한다.
- `pdf_object_key`만 추가했다. 발행일·초안 버전 컬럼과 최종 발송 검증은 후속 작업이다. 현재 개발 설정의 `ddl-auto=create`에 따라 테이블 생성 시 엔티티의 컬럼 정의가 자동으로 반영된다.

### 3.5 발송 이후 납기 재산정과 PDF

SENT 견적의 기존 납기 재산정 기능은 유지한다. 재산정으로 날짜가 달라져도 이미 발송한 PDF를 자동으로 덮어쓰지 않는다.
따라서 저장된 일정과 최초 발송 PDF의 날짜는 다를 수 있다. 변경된 일정의 PDF 생성·재발송은 이번 범위에 포함하지 않으며 별도 정책을 정한다.
이번 단계의 재발송은 보관된 동일 PDF의 재발송을 뜻한다.

## 4. 라이브러리와 폰트 준비 기준

- `build.gradle`에 OpenPDF 코어 `com.github.librepdf:openpdf:3.0.5`를 추가했다.
- OpenPDF 3.x는 `org.openpdf` 패키지를 사용한다. 기존 iText 예제의 `com.itextpdf`나 이전 OpenPDF 예제의 `com.lowagie`를 그대로 사용하지 않는다.
- 한글 폰트는 Google Fonts 공식 저장소의 나눔고딕 Regular·Bold TTF 원본을 사용한다.
- 두 폰트와 배포처의 `OFL.txt` 원문을 `src/main/resources/fonts/`에 함께 배치했다.
- 나눔고딕은 SIL Open Font License 1.1이며 상업적 사용, PDF 임베딩, 소프트웨어에 포함한 배포를 무료로 허용한다.
- 폰트를 배포할 때 저작권 고지와 라이선스를 보존한다. 폰트 자체만 단독 판매할 수 없고 수정본의 예약 이름 사용에도 제한이 있다.
- 폰트로 만든 견적 PDF 자체에 OFL을 적용할 의무는 없다. OpenPDF의 라이선스는 폰트와 별개다.

### 4.1 준비 결과 확인

- Java 25.0.3 환경에서 `dependencyInsight --dependency com.github.librepdf:openpdf --configuration runtimeClasspath`로 3.0.5 선택을 확인했다.
- Gradle `processResources`와 `compileJava`가 성공했다.
- `build/resources/main/fonts/`의 세 파일과 원본의 SHA-256 해시가 일치한다.
- 두 폰트의 TrueType 헤더와 `OFL.txt`의 저작권·라이선스 고지를 확인했다.
- PDF 생성 테스트에서 한글 텍스트 추출, Regular·Bold의 TrueType 폰트 임베딩, A4 한 페이지를 확인했다.

## 5. 초안 저장·PDF 생성 구현 결과

### 5.1 API

PDF API는 파일 바이트 대신 `application/json`으로 미리보기 정보를 반환한다.

| 요청 | 결과 |
|---|---|
| `POST /api/v1/quotations` | 제공하지 않음. 초안 저장은 POST PDF API에서 수행. |
| `POST /api/v1/quotations/pdf` | DRAFT 저장·커밋 후 PDF 생성·S3 저장. 201 미리보기 JSON. |
| `PUT /api/v1/quotations/{quotationId}/pdf` | 전체 입력으로 같은 DRAFT 수정·커밋 후 PDF 생성·S3 저장. ID·번호·최초 작성자 유지. 200 미리보기 JSON. |
| `POST /api/v1/quotations/{quotationId}/pdf/regenerate` | 기존 DRAFT 데이터로 재생성·S3 저장. 새 견적을 만들지 않음. 200 미리보기 JSON. |
| `GET /api/v1/quotations/{quotationId}/pdf` | 저장된 `pdf_object_key`로 조회 URL만 발급. 생성·업로드 없음. 경로가 NULL이면 409. |

성공 응답 필드는 `quotationId`, `quotationNo`, `clientCompany`, `clientEmail`, `previewUrl`, `expiresAt`이다. URL은 10분 유효하며 자격 증명의 잔여 유효기간에 따라 더 일찍 만료될 수 있다. PDF는 비공개 S3 객체로 유지한다.

- 모든 PDF API는 최고 관리자·수주 관리자만 허용한다. 생성·재생성·교체는 DRAFT만 허용하며 발송 이후 파일을 덮어쓰지 않는다.
- 성공·PDF 준비 실패 응답에 `Cache-Control: no-store`, `Location`, `X-Quotation-Id`를 설정한다. 프론트는 응답 본문의 ID를 사용하므로 커스텀 헤더 노출에 의존하지 않는다.
- S3 조회 응답에도 `Content-Disposition: inline`, `Cache-Control: no-store`를 지정한다.
- PDF 저장 서비스의 `create()`·`update()`가 초안 저장·수정 후 PDF 준비 순서를 제어한다. 기존 저장 트랜잭션을 커밋한 다음 PDF 준비를 실행하며, 실패해도 초안·신규 거래처·품목은 유지한다. 컨트롤러는 서비스 호출과 HTTP 응답만 처리한다.
- 재생성 전 경로 무효화를 별도 트랜잭션으로 커밋한다. 이후 최신 초안 읽기·생성·삭제·업로드·경로 저장을 DB 행 잠금 안에서 수행해 수정과 업로드가 겹치지 않게 한다.
- PDF 생성 성공 후 기존 파일 삭제를 시도한다. 삭제 실패는 로그를 남기고 업로드를 계속한다. 업로드 또는 URL 발급 실패 시 경로를 NULL로 유지한다. 경로 저장 커밋이 실패해도 성공 응답을 반환하지 않는다.
- 최초 저장 요청의 멱등성은 후속 작업이다. 실패 후 저장된 ID가 있으면 최초 POST를 반복하지 않고 POST 재생성 API로 재시도한다.
- 한 페이지 초과 등 입력 수정이 필요한 PDF 생성 오류는 400 `PDF_GENERATION_FAILED`, 준비·업로드 실패는 502 `PDF_PREPARATION_FAILED`, 경로 미준비 조회는 409 `PDF_NOT_READY`다.
- 위 PDF 오류 응답에는 `code`, `message`, `quotationId`, `retryUrl`을 담고 이전 `previewUrl`은 반환하지 않는다. 권한·존재 여부·초안 상태·입력 검증 오류는 기존 오류 응답을 따른다.
- `pdf_object_key` 컬럼과 S3 연동을 추가했다. 실제 S3 접근은 자동 테스트에서 모킹하며 이메일 발송·최종 SENT 확정은 이번 작업에 포함하지 않았다.

#### 프론트 연동 규칙 (이번 변경은 백엔드만 구현)

1. 생성·수정·재시도 시작 시 이전 iframe과 미리보기 URL을 비우고 로딩을 표시한다.
2. 최초 확인은 POST, 수정 후 확인은 저장된 ID로 PUT을 호출한다. 성공 응답의 거래처·수신 이메일·URL을 모달에 표시한다.
3. 502 오류에서 `quotationId`를 확보하면 POST 재생성을 한 번 호출한다. 다시 실패하면 오류 메시지와 수동 재시도 버튼을 표시한다. 400 오류는 입력 수정을 안내한다.
4. PDF 실패 후 경로가 NULL인 GET은 409를 반환한다. 이전 URL이나 S3 파일 존재 여부로 실패한 미리보기를 복원하지 않는다.
5. URL 만료 시 GET으로 URL을 갱신한다. PDF 준비 실패는 POST 재생성을 사용한다. 오래된 비동기 응답이 수정·닫기 이후 미리보기를 복원하지 않도록 요청을 취소하거나 응답을 무시한다.
6. 이 규칙은 API 연동 규격이다. 사용자 요청에 따라 프론트 저장소는 수정하지 않았다.

### 5.2 초안 수정 동작

- PUT은 PATCH가 아닌 전체 교체 요청이다. 기존 `CreateRequest`와 같은 필수 항목·품목 목록을 모두 전송한다.
- 최고 관리자·수주 관리자 권한, DB 계정 사용 상태와 비밀번호 변경 완료 여부를 다시 검증한다.
- 견적 행을 `PESSIMISTIC_WRITE`로 조회해 수정 트랜잭션을 직렬화한다. 여러 탭에서 이전 내용을 덮어쓰는 문제를 검출하는 버전 검사는 아직 없다.
- DRAFT만 수정할 수 있다. SENT·APPROVED·REJECTED·CANCELLED·EXPIRED는 거절하고, 존재하지 않는 ID는 404로 처리한다.
- 거래처·담당자·연락처 스냅샷·희망 납기·VAT·품목을 갱신한다. 견적 ID·번호·최초 작성자는 유지한다.
- 납기는 수정 당일의 생산 조건으로 재계산한다. 금액은 수정된 품목 수량·단가·VAT로 재계산한다.
- 이번 구현의 PDF 발행일은 최초 `createdAt` 날짜다. PUT 유효기간은 최초 날짜+7일 또는 +14일만 허용하고 생략하면 기존 값을 유지한다.
  3절 목표 설계의 날짜 변경 시 발행일 갱신은 아직 적용하지 않았다. 오래된 초안의 발행일·재발행 정책은 후속 작업이다.
- 초안 품목은 검증 후 기존 목록을 삭제·flush하고 새 목록으로 저장한다. 같은 제품을 다시 넣을 때 UNIQUE 제약 충돌을 방지한다. 품목 행 ID는 바뀔 수 있다.
- 견적·품목·신규 거래처는 하나의 수정 트랜잭션이다. 실패 시 원래 데이터로 롤백한다. 기존 거래처를 수정하거나 제거하지 않는다.
- PDF는 수정 커밋 이후 생성한다. PDF 실패 시 수정 결과와 ID를 유지하고 POST 재생성 API로 재시도할 수 있다.
- `Quotation.totalAmount`의 `updatable=false`를 제거해 초안 총액 갱신을 허용했다. 금액 변경은 DRAFT 전용 메서드로 제한한다.
- 수정과 PDF 업로드는 같은 견적 행의 DB 잠금으로 직렬화한다. 최종 발송은 미구현이며 향후 같은 잠금 규칙과 확인 내용 검증을 적용해야 한다.

### 5.3 공급자 정보와 샘플

공급자는 다음 값으로 표시한다. 기존 `quotation.pdf.supplier.*` 설정 주입은 제거했다.

| 항목 | 출력 |
|---|---|
| 회사명 | PRODFLOW |
| 담당자 | quotation.created_by에 저장된 최초 작성 직원 이름 |
| 사업자번호 | 000-00-00000 (예시) |
| 주소 | 서울특별시 예시로 123 (예시) |
| 연락처 | 02-0000-0000 (예시) |

담당자는 `QuotationDto.DetailResponse.createdBy`로 전달한다. 기존 `userName`은 연결된 직원의 현재 이름으로 계속 제공하며
PDF 공급자 담당자에는 사용하지 않는다. 다른 직원이 재생성하거나 작성자의 이름이 변경돼도 저장 당시 이름을 사용한다.
신규 DB 컬럼 없이 기존 감사 필드를 사용하며 요청 JSON으로 내부 직원 이름을 받지 않는다.

- 테스트용 데이터로 만든 확인 파일: `build/pdf-preview/quotation-draft.pdf`.
- 견적 관련 테스트로 PDF 폰트·한글·페이지 수, 초안 저장·수정, 생성 실패 후 데이터 유지·재생성, 권한과 기존 납기 재산정 회귀를 확인한다.
- PDF의 시각적 배치와 로고 반영은 사용자 검토가 필요하다. 테스트 통과는 모든 품목 조합의 한 페이지 출력을 보장하지 않는다.

## 6. 견적 거래처 필드명 변경

ERD의 quotation 컬럼명에 맞춰 엔티티와 API 이름을 통일했다. 값의 의미와 스냅샷 저장 방식은 유지한다.

| DB 컬럼 | 엔티티 필드 | API |
|---|---|---|
| `client_name` | `clientName` | 생성·수정 시 `Client.employee`에서 복사, 상세 응답 `clientName` |
| `client_email` | `clientEmail` | 상세 응답 `clientEmail` |
| `client_phone` | `clientPhone` | 상세 응답 `clientPhone` |
| `client_address` | `clientAddress` | 상세 응답 `clientAddress` |

- 생성·수정 요청의 최상위 `clientName`은 제거한다. 상세 응답은 `clientName`·`clientEmail`·`clientPhone`·`clientAddress`를 사용한다.
- `client.employee`와 `quotation.client_name`은 같은 거래처 측 담당자다. 생성·수정 시 선택한 Client.employee를 견적에 복사하며, 이후 거래처 정보 변경만으로 저장된 견적을 갱신하지 않는다.
- 신규 거래처는 `newClient.employee`에 담당자 이름을 입력한다. 이전 `representativeName`은 제거한다. `email`·`phone`·주소 입력 필드는 유지한다.
- quotation 초기 데이터의 컬럼 목록, Bruno 생성·수정 요청과 테스트도 새 이름으로 맞췄다.
- customer_order의 컬럼과 Client 엔티티는 변경하지 않았다. ERD의 client.employee 설명은 거래처 측 담당자로 정정했다.
- 기존 DB의 데이터나 컬럼은 자동 변경하지 않았다. 기존 데이터 보존 시 quotation의 기존 네 컬럼을 새 이름으로 변경하는 마이그레이션이 필요하다.
- 운영 DB에 현재 개발용 `ddl-auto: create`를 실행하여 이름 변경을 적용하지 않는다. 검증은 테스트 전용 H2 DB를 사용한다.
