# PRODFLOW — 내부 생산·수주 관리 플랫폼 기획서

생산시설 임직원이 **견적 → 수주 → 계약금 → 작업지시 → 포장 → 출고 → 배송 → 잔금**을 한 흐름으로 다루고, 상태와 이력을 남기는 내부 시스템이다.

> 현재 구현 로직 기준 요약이다. 상세 API·ERD는 PRD와 설계 문서를 참고한다.

## 1. 기획 개요

### 1.1 배경·목적

견적·수주·납기·출고를 수기와 유선으로 처리하면 누락과 혼선이 난다. PRODFLOW는 임직원만 쓰는 내부 전산화 시스템으로, 등록 검증·상태 이력·조회 집계를 한곳에 둔다.

### 1.2 사용자·역할

외부 회원가입과 거래처용 화면은 없다. 계정은 최고 관리자가 만든다.

| 역할 | 코드 | 하는 일 |
| --- | --- | --- |
| 최고 관리자 | `SUPER_ADMIN` | 계정·기준정보·라인·수주·생산 전반 |
| 수주 관리자 | `ORDER_MANAGER` | 견적·수주·거래처·품목(허용 범위)·라인·담당자 |
| 생산 현장 관리자 | `PRODUCTION_MANAGER` | 배정 작업 시작·정지·포장, 라인 가동·점검·고장 |
| 업무 조회 담당 | `INQUIRY_MANAGER` | 조회만 (등록·수정·상태 변경 없음) |

### 1.3 기대 효과

- 견적·수주에 등록 당시 값(스냅샷)이 유지된다.
- 계약금 전에는 생산을 시작하지 않는다.
- 배송 완료와 잔금 입금은 분리되어 있다.
- 대시보드는 저장된 계획과 상태만 집계한다.

## 2. 전체 업무 흐름

1. **견적 작성·발송**: 거래처와 품목(100개 이상)을 고르고 납기를 계산한다. PDF를 확인한 뒤 `SENT`가 된다. 견적은 공장 자리를 예약하지 않는다.
2. **승인**: 직원이 승인, 거절, 취소를 반영한다.
3. **수주 등록**: 승인 견적 기준으로 등록한다. 저장하면 `WAITING`(예정)이다.
4. **계약금 안내**: 상세에서 가상계좌를 발급하고 이메일로 안내한다.
5. **계약금 입금완료**: 생산대기(`CONFIRMED`)가 되고 작업지시와 생산계획을 만든다.
6. **생산 → 포장**: 작업이 전부 `PACK_DONE`이면 포장중 탭 대상이 된다.
7. **출고대기**: 직원이 `READY_TO_SHIP`으로 바꾼다.
8. **운송장 등록**: `SHIPPING`이 되고 잔금 결제를 준비한다.
9. **배송 완료**: 수주가 `COMPLETED`가 된다. 잔금은 별도로 입금된다.
10. **자동 취소**: 대기 상태이고 미입금인 수주는 계약금 마감일 다음 날부터 취소된다.

## 3. 주요 기능

### 3.1 계정·인증

- 로그인하면 Access Token과 Refresh Token을 발급한다. Refresh Token은 해시만 저장한다.
- 임시 비밀번호인 계정은 비밀번호를 바꾸기 전에는 업무 기능을 쓸 수 없다.
- 삭제는 Soft Delete이다.
- 권한은 API에서도 검사한다.

### 3.2 거래처

- 최고 관리자와 수주 관리자가 등록·수정한다.
- 거래처 등록시 도로명 주소 검색을 지원한다.
- 엑셀파일로 인한 거래처 일괄등록을 지원한다.
- 견적 작성 시 자동완성을 지원한다.
    - 거래처가 없으면 견적 저장과 함께 생성하고, 회사명이 같으면 기존 거래처의 정보들을 불러온다.
- 수주에는 해당 시점에서의 거래처 정보 스냅샷을 저장해 둔다.

### 3.3 생산품목·도면

- 항목은 모델코드, 제품명, 기종, 설명, 기준 단가다.
- 상태는 `AVAILABLE(생산가능)` / `DISCONTINUED(생산중지)`이다.
- 기종은 이미 등록된 기종을 고르거나, 없으면 새 기종명을 입력한다. 둘을 동시에 넣지 않는다.
- 목록과 검색은 페이징한다.
- 도면은 별도로 업로드한다.
    - 현재 도면은 Presigned URL(10분)로 보여 준다.
    - 응답에 `objectKey`는 노출하지 않는다.
    - 삭제하면 `replaced_at`을 기록하고 S3에서 파일을 지운다.

### 3.4 견적

- `DRAFT` → PDF(S3) → `SENT` → 승인 / 거절 / 취소 / 만료
- 납기 재산정은 `SENT` 상태에서만 한다.
- 수주가 등록된 뒤에는 견적 납기를 재산정하지 않는다.

### 3.5 수주

- 승인 견적 1건당 수주는 최대 1건이다.
- 수량은 견적 수량 이하, 품목별 100개 이상이다.
- 계약금은 총액의 50%이고 원 단위로 내림한다.
- 계약금 마감일은 등록일 + 3일이다.
- 계약금 발급은 수주 저장과 API가 분리되어 있다.

### 3.6 납기

- 가동 라인의 용량을 합하고, 등록이 빠른 수주를 먼저 채운다.
- 생산 시작일은 견적이면 오늘 + 3일, 수주면 계약금 마감일이다.
- 주말과 공휴일은 뺀다.
- 생산이 끝난 뒤 영업일 3일 후가 납기다.

### 3.7 수주 상태

- 대기(`WAITING`) → 생산대기(`CONFIRMED`) → 생산중 / 보류 → 포장중 → 출고대기 → 배송중 → 완료
- 입금 상태(`UNPAID` / `PARTIALLY_PAID` / `PAID`)는 진행 상태와 따로 관리한다.

### 3.8 결제·입금

- 입금은 PortOne 가상계좌 웹훅이나 수동입금으로 처리한다.
- 계약금이 `PAID`가 되면 생산대기로 바뀌고 작업지시를 만든다.
- 잔금은 운송장을 등록할 때 준비한다.
- 운송장 등록 시 배송 시작 SMS/EMAIL 알림은 현재 없다.

### 3.9 작업지시·라인

- 계약금이 확인되면 작업지시와 일자별 계획을 만든다.
- 작업 상태는 `PREPARE` → `PRODUCE` → `PACK` → `PACK_DONE` 순으로 진행하고, `SUSPEND`(일시정지)와 `HALT`(생산중지)가 있다.
- 라인 상태는 `AVAILABLE` / `OPERATING` / `INSPECTION` / `BROKEN`이다.

### 3.10 포장·배송

- 작업이 전부 `PACK_DONE`이면 출고대기 → 운송장 등록 → 배송중으로 진행한다.
- 운송장은 수주당 1건이고, 택배사 + 운송장 번호 조합은 중복될 수 없다.
- 배송조회가 실패하면 운송장 상태·수주 상태를 바꾸지 않는다.
- 탭: `PACKING(포장 끝)` / `READY_TO_SHIP(출고 대기)` / `SHIPPING(배송중)` / `BALANCE(잔고대기)`
    - 각 탭은 수주의 현재 상황에 따라 리스트로 조회한다.

### 3.11 대시보드·내부 알림

- KPI는 계획 수량과 상태 기반으로 집계한다.
- 납기 알림과 라인 알림은 내부 직원에게만 보낸다.
- 생산 일정 캘린더로 주간 생산 일정, 월간 생산 일정을 조회한다.

### 3.12 AI

- 대화방 단위로 Gemini / Groq를 사용한다.
- MCP, 읽기 전용 DB, SQL 검증을 거친다.
- 응답은 단발 JSON이다.
