## 1. 문제 발생

- 문제 유형
    - 목록 조회 페이징
- 현상 설명
    - `GET /api/v1/work-orders`에서 권한에 따라 한 페이지에 보이는 작업지시서 수가 달랐음.
    - 최고 관리자는 페이지당 5건이 보였지만, 생산 현장 관리자는 담당 작업이 여러 건이어도 1건만 보였음.
    - 화면에 보이는 건수와 응답의 `totalElements`, `totalPages`가 맞지 않았음.

---

## 2. 원인 분석

- 백엔드는 전체 작업지시서를 먼저 페이징해 `Page`로 반환하고 있었음.
- 프론트엔드는 응답 `content`에서 로그인한 사용자의 이름과 같은 행만 다시 거르고 있었음.
- 데이터베이스는 전체 기준 5건을 주고, 화면은 그 안에서 담당자 조건에 맞는 행만 남겼음.
- 담당 작업이 여러 페이지에 흩어지면 건수는 충분해도 각 페이지에는 일부만 보였음.
- `totalElements`와 `totalPages`는 담당자 필터 이전의 전체 건수로 계산됨.
- 담당자 필터보다 페이징이 먼저 실행된 순서가 원인이었음.

---

## 3. 해결 방법

- 프론트엔드의 담당자 이름 비교를 제거하고, 필터를 백엔드 조회로 옮김.
- `GET /api/v1/work-orders`에 `assignedId`를 추가해 담당자 ID로 먼저 거른 뒤 페이징함.
- 목록 쿼리와 `countQuery`에 같은 조건을 넣어 `totalElements`와 `totalPages`가 필터된 결과를 기준으로 나오게 함.

    ``` java
    and (:assigneeId is null or assignee.id = :assigneeId)
    ```

- 기존에는 전체 5건을 가져온 뒤 화면에서 담당자 행만 남겨, 담당 작업 3건이 서로 다른 페이지에 있으면 페이지마다 1건씩 보였음.
- 개선 후에는 담당자 ID로 먼저 거른 3건을 한 페이지에 보여 주고, `totalElements`는 3, `totalPages`는 1이 됨.

---

## 4. 배운점

- 화면에서 한 번 더 거르면 페이지 크기와 전체 건수가 조회 조건과 어긋남.
- 필터는 페이징 전에 적용하고, 건수 쿼리에도 같은 조건을 넣어야 함.
