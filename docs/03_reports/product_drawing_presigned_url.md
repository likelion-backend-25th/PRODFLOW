## 1. 문제 발생

- 문제 유형
    - 파일 저장소 보안 / API 응답 설계
- 현상 설명
    - 생산품목 도면을 S3에 업로드한 뒤, 미리보기·다운로드용 URL을 API 응답에 어떻게 내려줄지 결정해야 했음.
    - `objectKey`(예: `products/{id}/{uuid}_파일명`)나 버킷명을 응답에 그대로 포함하거나, 영구 공개 URL을 DB·응답에 저장하는 방식을 검토함.
    - 이 경우 저장 경로·버킷 구조가 외부에 노출되고, URL이 한 번 유출되면 만료 없이 계속 접근될 수 있는 위험이 있음.
    - 정보 수정 화면에서는 현재 도면 목록과 미리보기가 필요하므로, 접근 가능한 URL은 제공하되 저장소 내부 식별자는 숨겨야 했음.

---

## 2. 원인 분석

- S3에 실제 저장되는 식별자는 `objectKey`이며, 이 값만으로도 버킷 정책에 따라 객체 직접 접근을 시도할 수 있는 정보가 됨.
- API 응답이나 DB에 고정 URL을 저장하면
    - 권한 회수·파일 삭제 후에도 클라이언트가 옛 URL을 보유할 수 있음.
    - URL 만료(수명)를 서버가 통제하기 어려움.
- 따라서 도면 메타데이터(`ProductDrawing`)는 DB에 두고, 접근용 URL은 조회 시점에 짧게 발급하는 구조가 필요했음.

---

## 3. 해결 방법

- DB에는 `objectKey`, `fileName` 등만 저장하고, 응답 DTO에는 `objectKey`·버킷명을 포함하지 않음.
- 현재 도면 조회 API(`GET /api/v1/products/{id}/drawings/current`)에서
    - `StorageClient.createPresignedGetUrl(objectKey, 10분)`으로 시간 제한 조회 URL을 발급함.
    - 응답에는 `previewUrl`, `expiresAt`만 포함함.
- 업로드·목록 요약 응답에는 파일명·생성일시만 내려, 미리보기가 필요 없는 흐름에서는 URL 자체를 노출하지 않음.
- 삭제 시 DB에 `replacedAt`을 기록해 현재 목록에서 제외하고, S3 객체도 삭제하여 orphan 객체·잔존 URL 위험을 줄임.

흐름 요약:

- 저장: Multipart → S3(`objectKey`) + DB(`ProductDrawing`)
- 조회: DB에서 key 조회 → Presigned GET(10분) → `previewUrl`만 응답
- 삭제: `replacedAt` 기록 + S3 delete

---

## 4. 배운점

- 파일 저장 식별자(`objectKey`)와 클라이언트용 접근 URL은 분리해야 함.
- Presigned URL은 짧은 수명의 권한 티켓이므로, 유출되더라도 피해 구간을 만료 시간으로 한정할 수 있음.
- API 응답에 버킷·키 규칙을 노출하면 보안 리스크와 이후 저장 경로 변경 비용이 커짐.
