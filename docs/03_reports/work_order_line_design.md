## 1. 문제 발생

- 문제 유형
    - 작업지시서와 생산라인의 관계 설계
- 현상 설명
    - 하나의 수주 품목 수량이 생산라인의 일일 생산능력을 초과하면 여러 생산라인으로 작업을 나누어 배정해야 했음.
    - 작업지시서를 라인별로 여러 장 둘지, 한 장에 여러 라인을 연결할지 정해야 했음.
    - 라인별 수량뿐 아니라 담당자와 날짜별 생산계획도 함께 관리해야 했음.

---

## 2. 원인 분석

- `work_order`는 `line_id`를 하나만 가지므로, 작업지시서 한 장에 여러 생산라인을 직접 연결하기 어려웠음.
- 여러 라인에 생산량을 나누려면 작업지시서를 분리하거나 별도 라인 배정 테이블이 필요했음.
- 별도 배정 테이블은 관계를 유연하게 표현할 수 있지만, 테이블과 관리 로직이 늘어남.

---

## 3. 해결 방법

- 두 가지 방식을 비교함.
    - 1안: 수주 품목 하나에 작업지시서를 여러 장 두고, 장마다 라인·담당자·할당 수량을 관리.
    - 2안: 작업지시서 한 장을 유지하고, 별도 라인 배정 테이블로 여러 생산라인과 연결.
- 구현 기간과 관리 복잡도를 고려해 1안을 선택함.
- 작업지시서 한 장은 수주 품목 하나와 생산라인 하나에 연결함.
- 여러 라인에 나누어야 하면 작업지시서를 추가로 생성함.
- 날짜별 생산계획은 `production_plan`에 두고, 생산라인은 `work_order.line_id`에서 관리함.

    ```java
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_product_id", nullable = false)
    private OrderProduct orderProduct;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "line_id", nullable = false)
    private Line line;
    ```

- 채택한 흐름은 수주 품목, 작업지시서 여러 장, 라인별 담당자·수량, 날짜별 생산계획 순서임.
- 2안은 수주 품목, 작업지시서 한 장, 별도 라인 배정 테이블, 날짜별 생산계획 순서로 남김.

---

## 4. 배운점

- 작업지시서와 생산계획을 나눌 때, 라인은 작업지시서에 두고 날짜별 수량은 생산계획에 두는 편이 일정 조회가 단순해짐.
- 관계를 나누는 테이블을 늘리기 전에, 한 장이 한 라인만 담당하는 제약으로 충분한지 먼저 비교함.
