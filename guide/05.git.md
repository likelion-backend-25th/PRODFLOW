# 1. 브랜치 전략 개요 (Git-flow 기반)

## 1.1 브랜치 라이프사이클 및 역할
팀 프로젝트의 소스코드 무결성을 유지하고 안정적인 배포 환경을 구축하기 위해 Git-flow를 단순화한 브랜치 전략을 적용.

| 브랜치명 | 분기 출처 | 머지 대상 | 권한 및 보호 규칙 | 주요 역할 |
|---|---|---|---|---|
| main | - | - | 직접 푸시 금지, PR 승인 필수 | 운영 프로덕션 배포 전용 브랜치 (안정화 완료된 릴리스 코드 보관) |
| develop | main | main | Default Branch, 직접 푸시 금지, 2인 승인 및 CI 통과 필수 | 팀원들의 기능 개발 결과물이 통합되는 중심 개발 브랜치 |
| feature/* | develop | develop | 자유 푸시 가능, 작업 완료 후 PR 요청 | 새로운 기능 개발을 수행하는 개별 작업 브랜치 |
| fix/* | develop | develop | 자유 푸시 가능, 작업 완료 후 PR 요청 | 개발 중 발견된 버그 수정을 전담하는 개별 작업 브랜치 |

## 1.2 브랜치 네이밍 규칙
- 브랜치명은 소문자 알파벳, 숫자, 하이픈(-)을 사용하여 목적을 명확히 식별할 수 있도록 작성.
- 이슈 번호와 기능명을 결합한 형태 권장:
  - 기능 개발 브랜치: `feature/[이슈번호]-[기능명]` (예: `feature/12-course-list`, `feature/15-jwt-login`)
  - 버그 수정 브랜치: `fix/[이슈번호]-[버그명]` (예: `fix/23-progress-calc`)

# 2. develop 브랜치 생성 및 CI 파이프라인 구축

## 2.1 develop 브랜치 생성 및 기본 브랜치(Default Branch) 전환
- 목적: 팀원들이 저장소를 클론(clone)하거나 PR을 생성할 때 기본 타깃 브랜치가 develop으로 자동 지정되도록 구성.
- 설정 절차:
  1. 로컬 터미널에서 main 브랜치 기준으로 develop 브랜치를 생성하고 원격에 푸시:
    ```sh
    # 로컬의 main 브랜치로 이동
    git checkout main

    # 원격 저장소(origin)의 최신 커밋 내역을 로컬로 가져와 동기화
    git pull origin main

    # 최신 main 브랜치를 기반으로 로컬에 develop 브랜치 생성 및 전환
    git checkout -b develop

    # 생성한 develop 브랜치를 원격 저장소(origin)에 푸시하고 업스트림 추적 브랜치로 등록(-u)
    git push -u origin develop
    ```
  2. GitHub Repository 접속 > `Settings` 탭 선택.
  3. 좌측 메뉴의 `General` 선택 > `Default branch` 섹션 이동.
  4. 양방향 화살표(Switch branch) 아이콘 클릭 후 `develop` 선택 > `Update` 클릭.
  5. 경고 팝업창에서 `I understand, update the default branch.` 클릭하여 확정.

## 2.2 CI 워크플로우 파일 생성 및 푸시 (.github/workflows/ci.yml)
- develop 및 main 브랜치를 대상으로 PR이 생성되거나 커밋이 푸시될 때 자동으로 Gradle 테스트를 실행하는 파이프라인.
- 프로젝트 루트 디렉토리에 `.github/workflows/ci.yml` 파일을 작성하여 반영:

```yaml
name: CI Pipeline

on:
  push:
    branches: [ "main", "develop" ]
  pull_request:
    branches: [ "main", "develop" ]

jobs:
  build-and-test:
    runs-on: ubuntu-latest

    steps:
      - name: 소스코드 체크아웃
        uses: actions/checkout@v7

      - name: JDK 25 환경 설정
        uses: actions/setup-java@v6
        with:
          java-version: '25'
          distribution: 'temurin'

      - name: Gradle 실행 권한 부여
        run: chmod +x gradlew

      - name: Gradle 빌드 및 테스트 수행
        run: ./gradlew test
```

- 로컬 터미널에서 CI 워크플로우 파일 커밋 및 develop 브랜치로 푸시:
```sh
# 워크플로우 파일 스테이징 및 커밋
git add .github/workflows/ci.yml
git commit -m "ci: GitHub Actions 백엔드 빌드 및 테스트 워크플로우 추가"

# develop 브랜치로 푸시하여 GitHub Actions 첫 실행 트리거
git push origin develop
```

## 2.3 CI 파이프라인 최초 실행 확인
- GitHub Repository 상단의 `Actions` 탭으로 이동.
- 방금 푸시한 커밋에 대해 `HaruBaeum Backend CI Pipeline`이 실행되어 성공(`Green Check`)으로 완료되었는지 확인.
- 파이프라인 상세 화면에서 Job 명칭이 `build-and-test`로 정상 기록됨을 확인 (이 실행 이력이 생성되어야 3단원의 브랜치 보호 규칙에서 해당 Job 이름을 검색하여 등록 가능).

# 3. 브랜치 보호 규칙(Rulesets) 설정

## 3.1 develop 브랜치 보호 규칙(Rulesets) 설정
- 목적: develop 브랜치에 직접 커밋이 푸시되는 사고를 차단하고, 팀원 2인 이상의 코드 리뷰 승인과 CI 테스트 통과를 의무화.
- 설정 절차:
  1. GitHub Repository > `Settings` > 좌측 `Code, planning, and automation` 하위의 `Rulesets` > `Rulesets` 선택.
  2. 녹색 `New ruleset` 버튼 클릭 > `New branch ruleset` 선택.
  3. 기본 정보(General) 설정:
    - `Ruleset Name`: `develop-protection` 입력.
    - `Enforcement status`: `Active` 선택 (규칙 즉시 활성화).
  4. 대상 브랜치 타깃팅(Target branches):
    - `Add target` 버튼 클릭 > `Include default branch` 선택 (앞 단계에서 develop을 기본 브랜치로 전환한 경우) 또는 `Include by pattern` 선택 후 `develop` 입력.
  5. 세부 보호 규칙(Branch rules) 체크:
    - `Restrict deletions` 체크 (develop 브랜치 임의 삭제 방지).
    - `Require a pull request before merging` 체크 (직접 푸시 차단 및 PR 강제):
      - `Required approvals` 값을 `2`로 설정 (작성자 본인을 제외한 팀원 2명 이상의 Approve 승인 필수).
      - `Dismiss stale pull request approvals when new commits are pushed` 체크 (PR에 새 커밋이 추가되면 기존 승인을 무효화하고 재검토 유도).
    - `Require status checks to pass` 체크 (CI 테스트 통과 의무화):
      - `Require branches to be up to date before merging` 체크 (최신 develop과 충돌이 없음을 보장).
      - `Add checks` 버튼 클릭 후 2단원에서 실행된 테스트 Job 이름인 `build-and-test`를 검색하여 등록.
    - `Block force pushes` 체크 (강제 푸시 `git push -f` 차단).
  6. 최하단의 녹색 `Create` 버튼을 클릭하여 규칙 저장.

## 3.2 main 브랜치 보호 규칙(Rulesets) 설정
- 목적: 검증되지 않은 코드가 프로덕션 배포 브랜치로 유입되는 것을 방지.
- 설정 절차:
  1. `Settings` > `Rulesets` 화면에서 `New ruleset` > `New branch ruleset` 클릭.
  2. 기본 정보 설정:
    - `Ruleset Name`: `main-protection` 입력.
    - `Enforcement status`: `Active` 선택.
  3. 대상 브랜치 타깃팅(Target branches):
    - `Add target` > `Include by pattern` 선택 후 `main` 입력.
  4. 세부 보호 규칙 체크:
    - `Restrict deletions` 체크.
    - `Require a pull request before merging` 체크 (`Required approvals`: `2`, stale 승인 초기화 체크).
    - `Require status checks to pass` 체크 (`build-and-test` Job 등록).
    - `Block force pushes` 체크.
  5. 최하단 `Create` 버튼 클릭하여 저장.

## 3.3 CI 테스트 실패 시 브랜치 보호 동작 메커니즘
- PR이 생성되면 GitHub Actions 봇이 즉시 러너를 구동하여 컴파일 및 `./gradlew test`를 수행.
- JUnit5 테스트가 1건이라도 실패하거나 컴파일 에러가 발생하면 Status check 상태가 `Failure(X)`로 표시됨.
- 브랜치 보호 규칙에 의해 머지 버튼(Merge pull request)이 비활성화되며, 사유가 해결되어 테스트가 통과(`Success`)하기 전까지 코드 병합이 완전히 차단됨.

# 4. PR 템플릿 작성 및 코드 리뷰 가이드

## 4.1 PR 표준 템플릿 작성 (.github/PULL_REQUEST_TEMPLATE.md)
- 모든 팀원이 일관된 형식으로 작업 내용을 공유하고 셀프 점검을 수행할 수 있도록 프로젝트 루트에 `.github/PULL_REQUEST_TEMPLATE.md` 파일 생성:

```markdown
## 연관된 이슈
- close #[이슈번호]

## 작업 내용
- 변경 및 추가된 핵심 기능 요약 1
- 변경 및 추가된 핵심 기능 요약 2

## 중점 검토 사항 (선택)
- 리뷰어가 특별히 주의 깊게 봐주었으면 하는 로직이나 의사결정 사항 기술

## 체크리스트
- [ ] 브랜치 방향이 feature/* -> develop 인지 확인했습니다.
- [ ] 로컬에서 ./gradlew test 명령을 수행하여 모든 테스트가 통과함을 확인했습니다.
- [ ] 백엔드 코드 컨벤션(네이밍, 들여쓰기 4칸, DTO/Entity 분리)을 준수했습니다.
- [ ] 불필요한 콘솔 로그(System.out)나 미사용 import를 제거했습니다.
```

## 4.2 팀원 코드 리뷰 및 2인 승인 에티켓
- 리뷰어(Reviewer) 역할 및 피드백 종류:
  - `Approve`: 로직 및 컨벤션에 이상이 없으며 머지에 동의함. (최소 2인 이상 필수)
  - `Request changes`: 결함이나 심각한 컨벤션 위반이 발견되어 수정 전까지 머지를 보류함.
  - `Comment`: 단순한 질문이나 개선 아이디어를 전달하며 머지 가능 여부에는 영향을 주지 않음.
- 코드 리뷰 원칙:
  - 작성자의 인격이 아닌 코드 자체와 아키텍처 규칙에 집중.
  - 단순 지적이 아닌 "이유(Why)"와 "대안 코드(Alternative)"를 함께 제시.
  - PR 등록 후 슬랙이나 디스코드 팀 채널에 PR 링크를 공유하여 원활한 리뷰 요청 진행.

# 5. 로컬 작업부터 PR 머지까지의 실무 워크플로우

개발 작업의 시작부터 GitHub 원격 머지까지의 9단계 표준 명령어 가이드.

## 5.1 1단계: develop 브랜치 최신화
새로운 기능을 개발하기 전, 항상 최신 develop 코드를 로컬로 가져옴.
```sh
git checkout develop
git pull origin develop
```

## 5.2 2단계: 기능 브랜치 생성 및 이동
해당 작업의 이슈 번호와 목적을 브랜치명에 포함하여 생성.
```sh
git checkout -b feature/1-course-list
```

## 5.3 3단계: 로컬 코드 구현 및 단위 테스트 검증
비즈니스 로직과 API를 구현한 후, 로컬에서 전체 테스트를 구동하여 무결성 확인.
```sh
./gradlew test
```

## 5.4 4단계: 변경 사항 커밋 작성
코드 컨벤션(Conventional Commits) 규칙에 맞추어 커밋 메시지 작성.
```sh
git add .
git commit -m "feat: 강좌 목록 기본 페이징 조회 API 구현"
```

## 5.5 5단계: 원격 저장소로 기능 브랜치 푸시
```sh
git push origin feature/1-course-list
```

## 5.6 6단계: GitHub에서 PR(Pull Request) 생성
- GitHub 저장소 접속 후 `Compare & pull request` 버튼 클릭.
- base(목적지) 브랜치가 반드시 `develop`인지 확인.
- compare(출발지) 브랜치가 본인의 `feature/1-course-list`인지 확인.
- PR 템플릿 양식에 맞추어 작업 내용 작성 후 `Create pull request` 클릭.

## 5.7 7단계: CI 테스트 자동 통과 및 팀원 2인 승인 확보
- GitHub Actions CI 파이프라인이 구동되어 `All checks have passed` 초록불 확인.
- 팀원 2명이 코드를 검토한 후 `Approve`를 남겨 `2 approvals` 요건 충족.

## 5.8 8단계: PR 머지 및 원격 브랜치 삭제
- PR 작성자 또는 PL이 `Squash and merge` 선택 후 머지 실행.
  - Squash and merge를 적용하여 지저분한 자잘한 작업 커밋들을 깔끔하게 단일 커밋으로 압축 머지.
- 머지 완료 후 GitHub 웹 화면의 `Delete branch` 버튼을 클릭하여 원격 기능 브랜치 정리.

## 5.9 9단계: 로컬 develop 동기화 및 로컬 임시 브랜치 정리
```sh
git checkout develop
git pull origin develop
git branch -d feature/1-course-list
```

# 6. 브랜치 동기화 및 충돌(Conflict) 해결 가이드

## 6.1 충돌 발생 상황
본인이 `feature/1-course-list` 브랜치에서 작업하는 동안 다른 팀원의 PR이 먼저 `develop`에 머지되어 동일한 파일의 동일한 라인이 수정된 경우 GitHub PR 화면에 `Can't automatically merge` 경고 발생.

## 6.2 로컬에서의 안전한 충돌 해결 절차
원격 웹 UI에서 충돌을 해결하지 않고, 로컬 환경에서 충돌을 해결한 후 검증 커밋을 푸시.

1. 로컬의 develop 브랜치를 최신 상태로 갱신:
```sh
git checkout develop
git pull origin develop
```

2. 본인의 작업 브랜치로 이동 후 develop 브랜치를 머지:
```sh
git checkout feature/1-course-list
git merge develop
```

3. 충돌 파일 확인 및 수정:
- 터미널이나 IntelliJ IDEA의 충돌 해결 도구(Resolve Conflicts)를 활용.
- 충돌 마커(`<<<<<<< HEAD`, `=======`, `>>>>>>> develop`)를 검토하여 두 작업의 의도가 모두 온전히 반영되도록 코드를 수동 병합.

4. 로컬 테스트 재실행:
- 충돌 병합 후 코드가 깨지지 않았는지 반드시 테스트 재수행.
```sh
./gradlew test
```

5. 충돌 해결 커밋 생성 및 재푸시:
```sh
git add .
git commit -m "chore: develop 브랜치 변경사항 병합 및 충돌 해결"
git push origin feature/1-course-list
```
