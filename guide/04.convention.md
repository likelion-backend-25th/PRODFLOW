# 1. 코드 컨벤션의 정의 및 중요성

## 1.1 코드 컨벤션(Code Convention)이란?
코드 컨벤션은 프로젝트에 참여하는 팀원 전체가 하나의 개발자가 작성한 것처럼 일관된 가독성, 파일 구조, 문법 서식, 아키텍처 규칙을 유지하기 위해 사전에 합의하고 명문화하는 소프트웨어 개발 표준 규약.

## 1.2 코드 컨벤션이 필수적인 이유
- 팀 커뮤니케이션 비용 절감:
  - 서로 다른 스타일로 작성된 코드를 읽고 분석하는 데 소모되는 인지 부하를 최소화.
  - 코드 리뷰 시 들여쓰기나 변수명 같은 부차적인 서식 논쟁을 줄이고, 비즈니스 로직과 설계 품질 검증에 집중 가능.
- 잠재적 결함 및 런타임 오류 예방:
  - DTO와 Entity의 엄격한 분리, 생성자 주입 원칙, 트랜잭션 경계 설정 등 검증된 아키텍처 규칙을 강제하여 순환 참조나 지연 로딩 오류를 사전에 차단.
- 유지보수성 및 인수인계 효율 극대화:
  - 프로젝트가 확장되거나 팀원의 역할이 변경되더라도 일관된 구조를 유지하여 유지보수 생산성 보장.

# 2. 팀 프로젝트에서 반드시 정의해야 할 5대 핵심 영역

코드 컨벤션은 특정 서식이나 방식을 획일적으로 강요하는 것이 아니라, 팀원 간의 토론을 통해 프로젝트 상황과 팀 숙련도에 최적화된 기준을 사전에 합의하고 이를 일관되게 준수하는 데 목적이 있음.
아래 5대 핵심 영역별로 업계 표준 선택지와 대안(Alternatives)을 검토한 후, 팀별 킥오프 회의를 통해 프로젝트 표준을 자율적으로 결정하여 팀 문서에 반영함.

## 2.1 기본 언어 서식 (Style Guide)
프로그래밍 언어 차원에서 공통으로 준수할 서식 규칙을 결정함.

### 2.1.1 들여쓰기 (Indentation)
- 옵션 A (권장): 공백 문자(Space) 4칸. Java 및 Spring 진영의 공식 표준 관례이자 IntelliJ 기본값으로, 블록 구분이 뚜렷함.
- 옵션 B: 공백 문자(Space) 2칸. Google Java Style Guide 표준으로, 계층이 깊어질 때 가로 스크롤을 줄여주며 React 등 프론트엔드 코드베이스와 일관성 유지에 유리함.
- 공통 필수 규칙: Tab과 Space의 혼용은 엄격히 금지하며, 반드시 Space로 통일함.

### 2.1.2 최대 줄 너비 (Line Length)
- 옵션 A: 120자. 현대적 와이드 모니터 및 분할 뷰(Split View) 작업 환경에 적합한 권장값.
- 옵션 B: 100자. Google Java Style Guide 기준.
- 공통 필수 규칙: 제한 너비 초과 시 연산자나 쉼표 뒤에서 적절히 줄바꿈함.

### 2.1.3 중괄호 배치 (Braces Placement)
- K&R 스타일: 여는 중괄호는 선언문과 같은 줄 끝에 배치하고 닫는 중괄호는 새 줄에 단독 배치함. Java 및 JavaScript 전반의 사실상 표준.

### 2.1.4 제어문 중괄호 필수 여부
- 옵션 A (권장): 항상 필수(Force Braces). if, for, while 문이 한 줄이더라도 중괄호 생략을 금지하여 코드 수정 시 잠재적 버그를 예방함.
- 옵션 B: 단문 제어문 한 줄 허용. 코드 라인 수를 절약할 수 있으나 팀원 전원의 합의가 필요함.

### 2.1.5 Import 관리 규칙
- 옵션 A (권장): 와일드카드 import 금지. `import java.util.*;` 대신 단일 클래스를 명시적으로 import하여 클래스 이름 충돌을 방지함.
- 옵션 B: 패키지 내 클래스가 일정 개수 이상일 때만 와일드카드 허용 (IntelliJ 기본값: 동일 패키지 5개 이상 시 자동 축약).

## 2.2 식별자 명명 규칙 (Naming Conventions)
프로젝트 전반에서 사용할 고유 명칭의 명명법을 표준화함.

### 2.2.1 패키지 구조화 방식
- 옵션 A: 도메인형 구조 (Package by Feature / Domain-Driven). 도메인별로 하위 계층을 묶는 구조 (예: `domain.course`, `domain.member`). 도메인 응집도가 높고 MSA 및 멀티 모듈 전환에 유리하여 중대규모 프로젝트에 권장됨.
- 옵션 B: 계층형 구조 (Package by Layer). 아키텍처 계층별로 패키지를 구성하는 방식 (예: `controller`, `service`, `repository`, `entity`). 스프링 기본 구조에 친숙하고 직관적이어서 소규모 프로젝트에 적합함.

### 2.2.2 클래스 및 DTO 명명 패턴
- 클래스 및 인터페이스: 파스칼 케이스(PascalCase) 적용 및 역할 접미사(Suffix) 통일 (Controller, Service, Repository, Entity, Config, Exception 등).
- DTO 구성 방식:
  - 옵션 A (개별 클래스 분리): `CourseCreateRequest`, `CourseDetailResponse`처럼 역할별로 독립적인 클래스 파일 생성.
  - 옵션 B (정적 내부 클래스 통합): `CourseDto.CreateRequest`, `CourseDto.DetailResponse`처럼 상위 도메인 DTO 내부에 static class로 묶어 파일 개수 축약.

### 2.2.3 메서드 명명 패턴
- 옵션 A (Spring Data JPA 관례): `findById`, `findByStatus`, `existsByEmail`
- 옵션 B (MyBatis / SQL 관례): `selectCourse`, `insertCourse`, `updateCourse`, `deleteCourse`
- 옵션 C (비즈니스 도메인 관례): `register`, `modifySchedule`, `cancel`

### 2.2.4 상수 및 데이터베이스 식별자
- `static final` 상수는 대문자 스네이크 케이스(UPPER_SNAKE_CASE)로 작성.
- 데이터베이스 테이블명과 컬럼명은 소문자 스네이크 케이스(snake_case)로 일관되게 작성.

## 2.3 아키텍처 및 구현 표준 (Architecture Rules)
단순한 코드 서식을 넘어 백엔드 시스템의 안정성을 보장하는 핵심 설계 원칙을 규정함.

### 2.3.1 계층별 책임 분리
- Controller: 파라미터 수신, `@Valid` 기반 유효성 검증, 표준 응답 DTO 반환 (비즈니스 로직 작성 금지).
- Service: 비즈니스 유효성 검증, 도메인 엔티티 상태 변경, 원자적 트랜잭션 관리, DTO-Entity 간 변환.
- Repository: 데이터베이스 접근 및 쿼리 실행 전담.

### 2.3.2 DTO와 Entity의 분리 수준
- 옵션 A (엄격한 분리 - 권장): Controller와 Service 전 구간에서 Entity 노출을 금지하고 반드시 DTO로 변환하여 교환함. 순환 참조, 지연 로딩 오류, 민감 정보 유출을 원천 차단함.
- 옵션 B (Service 계층 내 Entity 활용 허용): 클라이언트와 접하는 Controller 계층에서만 DTO를 강제하고, 내부 Service-Repository 계층 간에는 Entity를 직접 교환하여 변환 코드 비용을 절감함.

### 2.3.3 의존성 주입(DI) 방식
- 생성자 주입 강제 (`final` 필드 + `@RequiredArgsConstructor` 적용). 필드 주입(`@Autowired`)을 지양하여 객체 불변성과 테스트 용이성 보장.

### 2.3.4 트랜잭션 관리 전략
- 옵션 A (권장): 클래스 레벨에 `@Transactional(readOnly = true)`를 기본 선언하여 힙 메모리 절약 및 읽기 최적화를 도모하고, 데이터 변경 메서드에만 `@Transactional`을 명시함.
- 옵션 B: 변경이 발생하는 메서드에만 명시적으로 `@Transactional`을 선언함.

### 2.3.5 전역 예외 처리 표준
- 비즈니스 커스텀 예외를 정의하고, `@RestControllerAdvice`에서 표준 에러 응답 객체(`ErrorResponse`)로 변환하여 일관된 JSON 에러 포맷 반환.

## 2.4 깃(Git) 협업 컨벤션
팀원들의 형상 관리 충돌을 방지하고 작업 이력을 명확히 추적하기 위한 버전 관리 표준.

### 2.4.1 브랜치 전략
- 옵션 A: GitHub Flow. `main` 브랜치와 기능별 `feature/*` 브랜치만으로 운영하는 단순한 모델. 빠른 개발과 배포 주기를 가진 4주 프로젝트에 적합함.
- 옵션 B: Git Flow (단축형). `main`(운영 배포), `develop`(통합 개발), `feature/*`(기능 개발)로 분리. 배포 버전과 개발 중인 최신 코드를 안전하게 격리할 때 적합함.

### 2.4.2 커밋 메시지 스타일
- 옵션 A: Conventional Commits 규격 (`feat:`, `fix:`, `refactor:`, `docs:`, `style:`, `test:`, `chore:`). 오픈소스 표준 규격으로 자동 릴리즈 툴 연동에 유리함.
- 옵션 B: 직관적 한글 태그 규격 (`[기능]`, `[버그]`, `[리팩토링]`, `[문서]`, `[설정]`). 팀원 간 작업 이력을 한눈에 식별하기 용이함.

## 2.5 코드 리뷰 및 머지 체크리스트
PR을 생성하고 승인하기 전 반드시 셀프 점검해야 할 항목을 표준 체크리스트로 정의함.

### 2.5.1 머지 승인(Approve) 기준
- 옵션 A: 팀원 1인 이상 승인 시 머지 허용. 빠른 개발 속도와 기능 구현 일정을 중시하는 팀.
- 옵션 B: 팀원 2인 이상 승인 시 머지 허용. 코드 품질 검증과 팀원 전체의 도메인 로직 이해를 중시하는 팀.

### 2.5.2 머지 방식(Merge Method)
- 옵션 A: Squash and merge. PR의 세부 커밋을 하나로 묶어 통합 브랜치 이력을 단순하게 유지함.
- 옵션 B: Create a merge commit. 분기 및 병합의 전체 타임라인과 개별 커밋 히스토리를 상세히 보존함.

### 2.5.3 체크리스트 점검 항목
- 빌드 및 테스트 통과 여부 (`./gradlew test`).
- 미사용 import 및 콘솔 출력 로그(`System.out.println`) 제거 여부.
- 팀에서 합의한 코드 컨벤션(네이밍, DTO 분리 등) 준수 여부.

# 3. 코드 컨벤션 작성 절차 및 운영 가이드

## 3.1 팀 단위 합의 및 산출물 작성 절차
1) 1단계 (공통 대안 스터디): 팀 프로젝트 시작 시 본 가이드 문서의 5대 핵심 영역별 대안 옵션을 팀원 전체가 검토함.
2) 2단계 (팀 맞춤형 규칙 확정): 팀의 비즈니스 도메인, 구현 기술 스택, 팀원 숙련도에 맞춰 토론을 통해 영역별 세부 규칙을 최종 합의함.
3) 3단계 (산출물 문서화): 확정된 규칙을 기획 산출물 폴더 내 `docs/01_planning/03_convention.md` 파일로 작성하여 저장소에 커밋함.
4) 4단계 (IDE 자동화 적용): 팀에서 결정한 서식 규칙(들여쓰기, 줄 너비 등)에 맞춰 모든 팀원의 IDE(IntelliJ)에 서식 자동화 설정을 완료함.
5) 5단계 (코드 리뷰 상호 검증): GitHub PR 템플릿과 연계하여 합의된 컨벤션 준수 여부를 상호 검증한 후 머지를 진행함.

- 💻 코드 컨벤션 정의서 샘플: [docs/01_planning/03_convention.md](../docs/01_planning/03_convention.md)

# 4. IntelliJ IDEA 서식 자동화 설정

팀 킥오프 회의를 통해 합의된 서식 규칙(들여쓰기 칸 수, 최대 줄 너비 등)에 맞추어 팀원 전원이 동일한 IDE 설정을 적용함으로써 서식 불일치를 사전에 방지함.

## 4.1 들여쓰기 설정
- 설정 경로: `Settings(Preferences)` > `Editor` > `Code Style` > `Java` > `Tabs and Indents`
  - Use tab character: 체크 해제 (공백 문자 강제)
  - Tab size: 팀 합의값 (기본 4 또는 2)
  - Indent: 팀 합의값 (기본 4 또는 2)
  - Continuation indent: Indent의 2배 (8 또는 4)

## 4.2 한 줄 최대 너비(Hard wrap) 설정
- 설정 경로: `Settings(Preferences)` > `Editor` > `Code Style`
  - Hard wrap at: 팀 합의값 (120 또는 100)
  - Wrap on typing: 필요 시 체크하여 타이핑 중 자동 줄바꿈 활성화

## 4.3 단문 제어문 중괄호 강제(Force Braces) 설정
- 설정 경로: `Settings(Preferences)` > `Editor` > `Code Style` > `Java` > `Wrapping and Braces` > `Control Statements`
  - 'if()' statement: `Force braces: Always` (팀 합의에 따라 설정)
  - 'for()' statement: `Force braces: Always`
  - 'while()' statement: `Force braces: Always`
  - 'do ... while()' statement: `Force braces: Always`

## 4.4 와일드카드 import 자동 방지
- 설정 경로: `Settings(Preferences)` > `Editor` > `Code Style` > `Java` > `Imports`
  - Class count to use import with '*': 99로 설정 (와일드카드 방지 시)
  - Names count to use static import with '*': 99로 설정

## 4.5 파일 인코딩(UTF-8) 설정
- 설정 경로: `Settings(Preferences)` > `Editor` > `File Encodings`
  - Global Encoding: UTF-8
  - Project Encoding: UTF-8
  - Default encoding for properties files: UTF-8
  - Transparent native-to-ascii conversion: 체크

## 4.6 파일 저장 시 자동 포맷팅
- 설정 경로: `Settings(Preferences)` > `Tools` > `Actions on Save`
  - Reformat code: 체크
  - Optimize imports: 체크
- 단축키 활용:
  - 코드 자동 정렬: `Ctrl + Alt + L` (Windows) / `Cmd + Option + L` (macOS)
  - import 문 최적화: `Ctrl + Alt + O` (Windows) / `Cmd + Option + O` (macOS)
